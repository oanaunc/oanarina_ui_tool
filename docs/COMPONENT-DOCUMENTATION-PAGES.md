# Local component documentation pages

UI-29-032 has a **partial local implementation**. It is an editable generated page, not a hosted documentation system or a claim of exact Figma automation parity.

In Design mode, select an ordinary main component or an instance and choose **Create documentation page** in the component inspector. The same action appears on local Assets cards and respects the exact selected variant. Enter a page name, optionally include all variants of its set, select **Review documentation page**, then **Generate documentation page**.

The new sibling page contains ordinary editable text: the title, component-set description when present, each component's description/documentation URL, variant values/description, and exposed property names, types, groups, defaults and descriptions. Instance-swap defaults display their main's name. This text captures the values at generation; it does not automatically overwrite later edits. URLs are plain text, with no remote fetch.

Each example is a normal linked instance created from its main's defaults. It follows later component edits and retains ordinary override/reset behavior. A selected instance's overrides are excluded. Examples are page roots, use the document/global modes and any modes authored on the main itself, and do not reproduce the main's source-ancestor appearance or enclosing layout context. A variant's property list describes that variant only. A generated page records which main it describes and a digest of the text it captured. The component inspector lists linked pages as up to date or out of date, and **Update page** rebuilds its generated text and examples in one Undo step. Layers you added stay, and edits to generated layers are replaced. Nothing updates without that click, and artwork changes need no update because examples are live.

Generation is a single normal editor edit and Undo step. Review does not change the document, history, selection or camera. Generation navigates to the new page. Save/reopen, page duplication and ordinary editing use the existing page/node model, plus one optional validated `documentation` field on the page; no migration is needed. Older `.oui` readers see normal text and instances to the extent they already support the source components. Existing pages, comments, root metadata (apart from the normal edited timestamp), component definitions, styles, variables and fonts remain unchanged. Nothing is published to a network or bundled into a library automatically. Existing related component metadata follows ordinary instance synchronization; unrelated private pages/comments are not copied into the generated page.

## Validation and limits

The source and prepared output are checked before publication. A private, immutable plan must still match the complete source, and normal shared component/layout/design-system derivation plus `.oui` parsing must preserve the exact prepared page and all original content. A failed or stale action adds no page or Undo entry. Source, mode, modal, Motion, selection, font revision and Assets-choice departures permanently invalidate retained controls; fresh controls can review again. Editing review choices invalidates the old prepared plan synchronously. Native Space/Enter ownership is contained within the review UI.

Supported source limits are 5,000 layers, 128 ordinary mains, 64 hierarchy levels and a conservative 20 MB source inspection budget. Variant lookup is bounded to 10,000 memberships. Generate at most 32 distinct variants; the combined dependency closure is limited to 32 mains/1,500 layers, each shared example preflight to 500 layers, all new page content to 4,000 layers and 200,000 text characters. Cumulative source/example inspection has a conservative 100 MB work budget, so a large source may require fewer variants. An example's visible extent must be at most 4,096 units per side, with a finite page extent within 100,000 units. Refusals are explicit; data is not silently truncated.

Slot-bearing, circular/missing/ambiguous dependency graphs, locked source hierarchies, video ownership, Whiteboard/Slides files, nested-main ownership, unsafe automatic ancestors and guide bindings owned outside their component definition are refused. Inner guide bindings use normal generated-owner remapping. Media/complex masks, unsupported external appearance contexts and very large components are not advertised as complete coverage. A source requiring a normal font/layout refresh must settle before review succeeds. Typography uses the shared renderer and installed/available fonts; no proprietary fonts are bundled. No native Mac reference round trip or Figma desktop parity verification was performed in this pass.

The narrow `canInstantiate` optimization applies only after finding an existing main and only for `parentId === null`. It skips an ancestor-cycle scan with no ancestors, preserving the original nonroot checks. Explicit closure/cycle preflight and final synchronization/parsing still reject circular documentation sources before publication.

## Evidence

- `tests/component-documentation.test.ts`: one-Undo generation and parse persistence, immutable originals, live defaults versus snapshot text, retained overrides, transformed sources, locks/slots, malformed mains/cycles, forged/stale plans, root graph operation count, 32 variants, maximum-source cumulative-work refusal, title controls, global/ancestor modes, private-comment separation and inner guide remapping.
- `tests/e2e/component-documentation.spec.ts`: actual linked red/green SVG pixels, normal save/reopen/Undo, native Space/Enter at 1280×720 and 125%, source/font/selection/document away/back refusal with fresh retry, identical-final local choices and exact Assets variant ownership.

Official reference context: Figma documents [component descriptions and documentation links](https://help.figma.com/hc/en-us/articles/7938814091287-Add-descriptions-to-styles-components-and-variables) and suggests [organizing component instances for developer handoff](https://help.figma.com/hc/en-us/articles/360040521453-Optimize-design-files-for-developer-handoff). These support the local workflow's purpose; they do not establish equivalence to every Figma documentation workflow. The reference-verification status remains pending.
