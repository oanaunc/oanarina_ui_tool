# Local library component lifecycle and usage

Forma supports advisory deprecation and current-file usage inspection for its local, immutable component-library snapshots. These workflows do not connect to a cloud library or collect analytics.

Open **Assets → Libraries → Component lifecycle and usage**. Choose a publishable component group, enter a reason, then mark it deprecated or restore it. A complete variant set shares one status across its variants. Each status change uses the normal document transaction, supports Undo and persists in .oui versions 1 and 2. Publishing a new local snapshot shares that source status. Existing linked instances remain usable; deprecation never replaces their geometry or disconnects their main component.

Incoming snapshot review shows its deprecation advice. Accepting an update follows the existing explicit update/conflict workflow and stores the accepted status in that file. A restored incoming component has no deprecation warning; the installed status changes only when the update is accepted. Availability and deprecation are separate: disabling a dependency or removing its source snapshot does not delete cached definitions or references.

The usage list matches stable library identities, source-to-local node maps and accepted definition baselines. It counts actual instance nodes across every page, including hidden and locked instances. It separates authored instance roots, generated nested instance nodes and references inside main-component definitions; these categories are not estimates of user actions or visual occurrences. Different libraries with the same component names and source IDs remain separate. Copied local definitions have no publication ownership and do not inflate the original library’s usage. Selecting a reference navigates to its actual page/layer without changing document history. Missing mains and incomplete older baselines produce explicit diagnostics; unverifiable set variants are not guessed by name.

Source status is optional `libraryPublication.deprecations`, keyed by `component:<source root ID>` or `set:<source set ID>`, with a plain-text reason of 1–1,000 characters. Up to 512 groups are allowed. A deleted or no-longer-publishable source retains an unavailable reference that can be explicitly cleared. It is omitted from later publication with a notice; a different component with the same name never inherits it. Source locks and component ownership are checked before writes. Closing the lifecycle disclosure invalidates its retained edit controls; reopening starts a new local session. Changing usage filters or paging invalidates retained navigation from hidden rows.

Snapshot schema 1 gains the optional group status both at the root and in its validated asset manifest. A present status participates in the asset fingerprint. An absent status preserves the previous fingerprint algorithm exactly, so old snapshots and unmodified asset identities remain compatible. Installed status is optional metadata; .oui version numbers are unchanged. Malformed status, inconsistent manifests and forged references are rejected before importing or updating the document. Publishing records history while retaining source status.

Inspection scans at most 100,000 document layers, source ancestry up to 128 levels and usage ancestry up to 256 levels. Accepted baseline inspection is capped at 12 MB of UTF-8 text. The UI renders 24 component groups and 50 instance references per page. Existing snapshot, installed dependency and project bounds also apply. Reports describe this file only, including accepted cached definitions; they do not scan other files, measure remote usage, record insertion events or prove a component is unused everywhere.

Figma Bridge validates the added metadata before mutation, omits status/reasons and reports that omission. Existing editable component linkage follows its normal independent limitations. API mock tests are not a native Figma round trip. There is no individual-variant deprecation, upstream deprecation service, automatic replacement migration, cached-file analytics or deprecation enforcement. UI-29-019 and UI-29-021 remain **partial** for those broader reference workflows.
